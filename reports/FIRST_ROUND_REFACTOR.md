# 第一轮：TaskController、AgentLoop 与消息完成边界

实施日期：2026-09-10。范围是已讨论的核心第一轮，沿用现有功能和展示，不在本轮扩展业务场景。

## 语言与模块

新核心采用 TypeScript。现有后端已经运行在 Node，取消信号、流式模型请求、进程执行和测试均可复用；TS 用于明确消息、决策结果和控制接口，避免在这轮重写整套运行环境。未来 Python 数据处理可以通过工具执行适配器接入，这只是扩展建议，本轮没有新增 Python 执行入口。

运行要求提升为 Node.js 24.12+；开发时复用前端依赖中的 TypeScript。Node 执行时去除类型，不执行类型检查，所以 `typecheck:runtime` 是单独检查项。配置启用 `strict`、`noUncheckedIndexedAccess` 和 `erasableSyntaxOnly`，TS 核心不使用 `any`。相关运行方式见 [Node 官方 TypeScript 说明](https://nodejs.org/docs/latest-v24.x/api/typescript.html)。

| 模块 | 本轮职责 |
| --- | --- |
| `server/runtime/contracts.ts` | 控制状态、消息来源、执行租约、单步结果和适配接口 |
| `server/runtime/task-controller.ts` | 单一活动驱动、epoch、消息接纳、改方向、取消、完成判定 |
| `server/runtime/agent-loop.ts` | 一次上下文准备、模型请求、完整工具交互和结果配对 |
| `server/runtime-adapter.mjs` | 将核心接到现有模型、上下文、事件、任务和资源登记 |
| `server/harness.mjs` | 保留对外入口及本轮尚未拆分的外围能力 |

依赖从 Harness 经过适配层指向核心。核心没有导入 Harness、HTTP、文件系统、模拟场景或能力目录；可以用纯内存接口测试。适配层仍与现有任务对象耦合，旧 `.mjs` 并未全部纳入严格类型检查，不能宣称已完成整个后端的 TS 迁移。

## 控制行为

每个 Agent 由一个控制器持有活动执行。重复唤醒返回同一执行句柄。改方向使旧 epoch 失效并发出取消信号，等待旧驱动返回后再运行新驱动。连续调整不会启动并发的有效循环；全部消息按接收顺序保留，业务上最新目标由既有入口更新。

模型请求与每次工具派发前检查执行租约。即使模型适配器忽略取消信号并返回迟到响应，该响应也不能继续派发工具。对已经完成的操作保留实际结果，对尚未执行的同轮调用补齐取消结果，维持调用与结果配对。取消不回滚已经完成的副作用。

邮箱消息带有 ID 和来源。先将整批输入同步接纳到上下文，再发出“已消费”通知；通知期间的改方向不会丢掉已接纳输入。停止任务时，未接纳输入通过 `inbox.discarded` 显式记录丢弃原因。来自子任务的内容带来源说明进入模型上下文，不作为用户新增授权。

纯文本模型响应是完成候选。控制器在没有待收消息、待切换模型、未结束子任务和登记中的在途工作时才提交完成；检查与提交之间没有 `await`。父任务仍开放时，子任务的成功、失败和取消结果均通过邮箱投递。完成事件的观察者如果立即提交后续消息，控制器会等旧驱动释放后开始新一轮，不把输入留在已完成任务里。

上述完成边界对父任务当前登记的工作负责。进程管理器如果漏掉真实存活进程，控制器不能从空登记表推断出这类进程；这仍属于资源管理层待修复的问题。

## 测试驱动记录

先新增 5 个 Harness 回归场景并运行：最终回答期间的用户追加、子任务成功、子任务失败、完成通知期间的新输入均失败，停止后迟到回答的场景通过。拆分并修复后，5 项全部通过。

随后先补充输入接纳竞态测试，复现“发布已消费事件时改方向，后台证据没有进入后续模型上下文”；调整接纳与通知顺序后通过。另一个纯核心测试先复现“thinking 通知触发取消后仍发送模型请求”，增加请求前检查后通过。

本轮新增 16 项测试：6 项现有 Harness 的集成回归，10 项 TS 核心测试。核心覆盖重复唤醒、连续改方向、停止时丢弃队列、等待后台结果、切换阻止提前完成、输入准备中取消、迟到流和工具请求、通知重入、已完成工具效果及取消结果配对、无效 JSON 不执行等边界。

## 本轮之后仍然存在的边界

`Harness` 内仍有 Supervisor、工具分发、授权和模型交接，后续拆分应继续以对应的失败用例约束行为。此前确认的子任务初始化失败清理、进程组漏回收、工具与 Skill 版本固定、大输出证据保全、模型交接旧证据、路径策略和动作缓冲问题，均未由这一轮解决。核查基线保留在 `CORE_MECHANISM_STATUS.md` 和 `CODE_REVIEW.md`，其中旧行号和复现脚本描述的是重构前版本。

控制状态仍通过窄接口接入既有 Agent 对象，HTTP 和工具入口还有少量外围状态更新。消息保证限于进程内的顺序接纳，没有实现崩溃后可重放的持久邮箱或跨进程事务。适配器如果永远不响应取消且永远不返回，新轮次会继续等待；实际模型和执行适配器仍需提供各自的超时与终止机制。

本轮没有把“已消费消息”当成“模型已处理正确”的证明，也没有实现模型回答质量评测。代码验证的是输入、调用、结果与控制状态的边界。
