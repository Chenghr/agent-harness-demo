# 10-手动测试与录屏操作手册

这份手册用于你自己操作、检查结果并录屏。命令按 macOS 编写，界面名称按当前代码核对。这里的“预期”是你需要核实的结果，不表示已经用你的模型账号跑过。

按顺序完成环境准备、八人祝福网站、补充机制测试，可以分段录制。最后一节给出约 20 分钟的展示顺序。

**模拟模式只处理内置演示流程。** 网站主线、自由分工和普通工作区任务请选择真实对话模型。内置场景用于稳定观察控制机制，不能当作真实模型完成任意任务的证明。

## 一、录屏前准备

### 1. 启动应用

在终端 A 执行：

```sh
cd /Users/chr/Documents/华为/agent-harness-demo
node --version
```

需要 Node.js 24.12.0 或更新版本。首次运行或依赖有变化时，依次执行：

```sh
npm ci
npm --prefix web ci
npm run build
npm start
```

已经安装并构建过，只需 `npm start`。如果 4317 上已经是当前应用，直接复用，不要重复启动。录制期间保持终端 A 和电脑运行；不要按 Ctrl+C。

另开终端 B：

```sh
cd /Users/chr/Documents/华为/agent-harness-demo
curl -fsS http://127.0.0.1:4317/api/health
open http://127.0.0.1:4317/
```

预期：健康接口返回正常状态，浏览器打开工作台。本文统一使用 4317，不混用开发模式的 4318。

### 2. 在网页保存真实模型配置

点击左下角“模型与运行设置”。密钥填写放在录屏之前完成。

1. 在服务配置中填写“服务名称”“协议”“API 地址”“API 密钥”，点击“保存服务”。协议选服务实际支持的 Chat Completions 或 Responses。
2. 添加模型：选“所属服务”，填写实际“模型 ID”，把“显示名称”设为便于辨认的“对话模型 A”。上下文上限、输出上限、输出参数、思考等级按供应商资料填写。
3. 点击“保存模型”，再点击该模型的“测试调用”。需要通过实际工具调用测试。
4. 用同样方式配置“对话模型 B”，供切换测试使用。可以来自同一服务，但要使用你确实有权限调用的模型。

不要把“获取模型列表”讲成自动验证了模型容量。这里的容量来自配置；测试调用也不证明长任务质量。

展开“出图与网站发布服务”：

1. 添加“出图服务 A”，填写图片 API 地址、模型 ID、协议和密钥，点击“保存出图服务”。
2. 如果要验证更换图片模型，再添加“出图服务 B”。必须是真正不同的可用配置，不能只改显示名称就宣称换了模型。
3. 需要公开发布时，填写 Netlify 的已有测试站点 ID、Token 和 API 地址，点击“保存发布服务”。选择专用于演示的站点，因为确认发布会更新这个站点。

当前图片接口接收文字描述，返回 Base64 图片；不支持照片参考、图片编辑或仅返回下载链接的协议。不要把文本聊天模型 ID 填进图片模型栏。

如果换了终端，先用刚才打印的实际目录重新设置 `HARNESS_DEMO_ROOT`，不要重新生成材料后继续检查旧任务。

### 4. 先做一次真实出图预检

选真实“对话模型 A”，新建一个单独的任务，发送：

```text
这是出图接口预检。请发现并加载 image_models、image_generate，列出已配置的出图服务，选择“出图服务 A”。生成一张 key 为“接口预检”的虚构卡通头像：浅色背景、简洁线条，不参考任何真人照片。完成后报告实际使用的模型和图片版本，不创建网站、不申请发布。
```

点击“图片与网站”，确认能看到真实图片和模型记录。有第二个图片服务时，用相同方式预检 B。

预期：看到图片，实际模型与配置一致。如果只得到错误或空图，先解决接口问题，再录网站主线。预检产生的图片不作为主线任务的成员素材。

## 二、主线：八人祝福网站

### 5. 准备一个可控的出图失败

这一小节故意让一个本机接口返回错误，用来稳定复现失败隔离。它不是实际图片生成服务，也不能用于展示图片质量。

另开终端 C 执行，保持运行：

```sh
node --input-type=module <<'NODE'
import http from 'node:http';
const timers = new Set();
const server = http.createServer((req, res) => {
  req.resume();
  if (req.method === 'GET' && req.url === '/health') {
    res.writeHead(200, { 'Content-Type': 'text/plain' });
    res.end('manual failure fixture ready\n');
    return;
  }
  const timer = setTimeout(() => {
    timers.delete(timer);
    if (res.destroyed) return;
    res.writeHead(503, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify({ error: { message: 'MANUAL_IMAGE_FAILURE：录屏主动注入的出图错误' } }));
  }, 3000);
  timers.add(timer);
  res.on('close', () => { clearTimeout(timer); timers.delete(timer); });
});
server.listen(4326, '127.0.0.1', () => console.log('故障接口：http://127.0.0.1:4326/v1；Ctrl+C 退出'));
process.on('SIGINT', () => {
  for (const timer of timers) clearTimeout(timer);
  server.closeAllConnections();
  server.close();
});
NODE
```

在网页“出图与网站发布服务”添加：

- 服务名称：`录屏故障接口`
- 图片 API 地址：`http://127.0.0.1:4326/v1`
- 图片模型 ID：`manual-failure`
- 图片协议：兼容 Images API（指定 b64_json）
- API Key：留空


点击“图片与网站”，展开“祝福网站的成员与字数要求”，在“参与成员，每行一位”粘贴：

```text
王磊
李明
张琳
陈晨
刘洋
赵悦
周宁
孙晴
```

此时字数上限留空，点击“保存网站要求”。关闭弹窗，点击“运行详情 → 任务树”。

讲解：“先明确要交付哪些人的成果，后面生成网站会按这份名单检查。现在还没有公开发布。”

### 7. 创建后台任务，观察单人失败隔离

回到主对话，保持“下一步补充”，发送：

```text
开始第一批后台工作。请先读取 members.json，并通过 image_models 查到服务的实际编号。

创建三个后台通用助手，目标分别为“王磊头像”“李明头像”“祝福文案”。明确传递成员信息和必要材料，不让子助手自行猜测背景。

王磊头像：只通过 modelId 明确指定“录屏故障接口”，调用 image_generate，key 使用“王磊”。这是主动注入的错误，报告实际错误后结束，不自动重试、不换服务。
李明头像：使用“出图服务 A”，key 使用“李明”。统一风格是浅色背景、圆形构图、简洁插画、虚构人物，不使用真人照片。成功后保留图片版本。
祝福文案：分配 members.json；原样保留其他人的祝福。先单独请求将李明原文写入自己工作目录的 outputs/li.txt，等待用户批准。这次工具交互不要同时提交王磊或其他人的写入。李明写入完成后，在下一次决策先读取用户的新补充，再处理王磊并写入 outputs/wang.txt，最终返回八个人的完整文案。

三项都用后台方式创建。出图失败只报告对应成员，不取消其他任务。请返回分工和任务编号，让主对话可以继续交流，暂不搭网站。
```

预期：任务树出现三个独立子任务；王磊的工具记录包含故障错误，李明和文案工作继续。主任务可以接收消息。

**看到文案助手对 `outputs/li.txt` 的写入批准请求后，先不要批准，执行下一步。** 当前后台助手的文件写入需要批准，这个状态为手动操作留出窗口。默认子任务时限是 3 分钟，提前准备好下一条提示词，不要在批准处长时间停留。

故障接口直接验证的是“单人出图调用失败后，其他工作不受影响”。模型可能把错误整理成一个正常返回的失败说明，而不是让子任务状态变成“失败”。不要混淆这两种结果；整个子任务异常退出的隔离，由第 25 步的 A1 测试另行验证。

### 8. 给文案助手定向补充，同时换它的对话模型

1. 在主输入框上方的“补充消息发给谁”，选择“只发给：祝福文案”。
2. 保持“下一步补充”，发送：

```text
王磊那段压到 50 字以内，别动别人的。李明这一段继续按已提交的原文写入，后续不要再改；保留另外六个人的原文。最后给出王磊实际字数和完整八人文案。
```

3. 在任务树的“祝福文案”卡片，把“切换子助手模型”改为“对话模型 B”。
4. 核对 `outputs/li.txt` 的待写内容，点击“仅本次允许”。等待下一次模型调用；后续 `outputs/wang.txt` 的写入也检查并仅允许本次。查看文案结果、事件和实际模型。

预期：补充进入这个助手的下一次决策；李明的文件不再次写入；其他头像任务不取消；只有文案助手切换到 B，主助手仍用 A。切换请求可能先显示等待，只有后续请求实际使用 B 才算验证完成。

再打开“图片与网站”，把“字数上限”填为 `王磊=50`，点击“保存网站要求”。这是为网站成品增加检查，不替代刚才发送给文案助手的定向消息。

讲解：“用户补充先进入目标助手的消息队列，当前工具调用完整结束后再生效。换模型也在这个边界处理，不把已经发生的写入撤掉。”

如果操作时助手已经结束，本次只能验证“重做”，不能算运行中补充或切换。重新建立这三个子任务的测试，或用第 25 步的 B1、E 测试补充证据。

### 9. 在出图后台运行时继续主对话

将接收对象切回“发给主助手，由它安排”，发送：

```text
继续生成张琳、陈晨、刘洋、赵悦、周宁、孙晴六个人的头像，每人独立后台任务，使用出图服务 A，沿用李明的风格，每人的 key 就是姓名。已有成功头像不要重做，王磊暂不重试。请保留至少一个后台名额，分批创建并汇报分工。
```

看到头像任务仍在运行时，再发：

```text
先给我三句适合放在网站顶部的教师节开场白。后台出图继续，不要取消，不要等待所有图片完成才回答我。
```

预期：主助手处理这条消息时，仍有相同编号的头像子任务运行。保存这一段录屏，作为“主对话继续、出图在后台”的直接证据。

不要只拍“新建任务”按钮；新建另一段对话和在同一任务中继续交谈，是两个不同的测试。

### 10. 单独重做王磊，并验证图片模型切换

将接收对象切回主助手，发送：

```text
请创建一个“王磊头像重做”后台通用助手，只重做王磊，不动其他成员。给它以下明确背景：通过 image_models 选择“出图服务 A”，key 仍为“王磊”，沿用浅色背景、圆形构图、简洁插画、虚构人物的风格，不访问相册。成功后，单独请求把本次图片编号写入自己工作目录的 outputs/wang-image-version.txt，等待用户批准。写入完成后，在下一次决策先读取新消息，没有新要求再结束。不要在同一次工具交互里预先生成第二版。
```

预期：新建一个王磊任务，原来的错误记录和其他人的结果保留。

如果还要测试“重做此任务”按钮：趁仍有后台工作时，在任务树下方“后台任务目标或补充”填入上面针对助手的具体要求，再点击原王磊节点的“重做此任务”，用它替代主对话创建。按钮会保留与原任务的关联。输入栏只在任务活跃时出现；不要对已经结束的任务直接发送补充。两种走法选一种，避免同时生成两份重做任务。

第一张图片成功、等待 `outputs/wang-image-version.txt` 写入批准期间，在新节点把“切换出图模型”改为“出图服务 B”，再通过定向消息给这个新助手发送：

```text
在当前写入完成后，使用我刚选择的出图模型，再生成王磊的第二个版本。key 仍为“王磊”，风格保持统一。其他成员不动。报告两次出图各自实际使用的服务和版本。
```

核对待写内容，点击“仅本次允许”，等待第二次出图。预期：“图片与网站”中出现王磊的两个成功版本，分别记录 A、B；其他七人的成功版本不变。正在执行的图片请求不会被中途换掉，新的选择作用于下一次出图。

如果没有 B，只做 A 下的单人重做与版本测试，并将“图片模型切换”记为未测试。不要用同一模型改名替代验证。单次图片请求有超时，子任务也有总时限；两次慢出图加人工等待可能超时，预检时应先测实际耗时。发生超时要记录，不把新建两个助手分别出图说成同一助手中途换模型成功。

### 11. 让后台助手搭站，检查八人和 50 字要求

将接收对象切回主助手，发送：

```text
请汇总现有结果，使用文案助手返回的完整八人文案和每位成员当前选中的成功图片。王磊祝福必须在 50 字以内。

创建“网站组装”后台助手；通过 agent_spawn 的 images 明确分配这八个图片版本，把八人姓名、文案和字数要求写进背景。让它调用 greeting_site 生成统一样式的本地预览，返回预览编号；不要申请发布。不要重新出图，不要把王磊的故障版本作为素材。
```

预期：出现网站后台节点，材料范围里有明确分配的图片版本；“图片与网站”显示完整预览，包含八个人和对应图片。检查王磊文案，而不是只看助手说“已检查”。

讲解：“后台搭站助手拿到的是明确分配的图片版本和文案。成员遗漏、重复或指定文案超长时，网站工具会拒绝生成这个祝福网站预览。”

这里的 `greeting_site` 使用内置统一版式，不代表任意网页设计都能达到同样效果。搭站过快时不要强求现场插入聊天；第 9 步和自动测试分别提供同任务后台继续的证据。

### 12. 只恢复王磊旧图，再生成新预览

1. 打开“图片与网站”，在王磊第一版上点击“使用此版本”。
2. 确认“当前版本”移动到第一版，其他七人的当前版本不变。
3. 关闭弹窗，发给主助手：


预期：生成新的预览版本；王磊使用旧图，其他成员保持原样。

**选择旧图不会直接改写已经生成的固定预览。** 必须重建并检查新预览，再申请发布。旧预览作为历史版本保留。

### 13. 申请发布，关闭网页后恢复

这一小节要求已配置 Netlify 发布目标。如果没有，完成本地预览即可，把发布和发布批准恢复记为“待真实服务测试”。

5. 在终端 B 执行：

```sh
open http://127.0.0.1:4317/
```

预期：自动恢复刚才的会话；展开任务树和“图片与网站”，原来的成员结果、预览编号和待批准发布仍在，不需要重新创建任务或重新申请发布。

讲解：“关掉的是显示页面，执行和记录由后端管理。后端关闭、电脑休眠或外部请求中断，是另一个问题，不能用这次恢复来证明它们都能自动续跑。”

### 14. 用户批准后公开发布

继续检查待发布版本和目标站点。确定是准备公开的演示内容后，点击“确认公开发布此版本”。

讲解：“模型能提出发布申请，最终发布由用户在页面批准。批准对应刚才看过的固定版本，完全访问模式也不能跳过这一步。”

3. 查看原文、风险和建议分类，选择“保留并存，确认后启用”，勾选目标类别，点击“确认本项处理”。记录详情中的“实际调用名”。

预期：目录保留两份不同内容，实际调用名可区分；重名时不会静默覆盖旧版。内容完全重复与名称相同但内容不同，处理证据不同。

选择可用的真实评估模型后，可以点击“用所选模型比较候选”，查看功能重叠意见，再由自己决定。相似功能意见是审查建议，不是已经证实的冲突结论。

讲解：“先扫描并给出建议，是否跳过、并存或启用新版由人决定。人和模型都沿着同一棵场景目录逐层查看，不一次塞入上千份正文。”

### 16. 独立质量评估和安全评估

如果只选“仅规则检查 · 不生成完整质量分”，或评估未完成、内容未完整覆盖，不应把结果当作完整模型评分。报告评价的是这份 Skill 本身，不是证明它一定改善后续业务效果。

再导入 `skills/photo-risk`。查看相册、真人脸相关风险提示。为后面的加载测试，可选择“保留并存，确认后启用”，并记录实际调用名；不要标记为已核实的可信来源。

讲解：“风险扫描、来源记录、质量评价和执行权限是分开的。这里启用风险反例只是允许读取说明，不是允许它读取相册。”

预期：阶段范围变化，最后从活跃 Skill 中移除。当前文件包很短，只用于观察分段机制；千级数量和长上下文压力另测，不把这三个短文件说成“超长 Skill 性能测试”。

如果模型直接搜索而没有逐层浏览，记录本次实际路径，不能宣称验证了逐层选择。可以补充指令让它按层浏览，并保留第一次未遵循的结果。

## 四、补测权限、回滚、打断和上下文

### 19. 三种权限模式

先让之前占用“权限与回滚工作区”的任务结束；新建真实模型任务，选择这个工作区。不要选择教学示例工作区做这项测试。

在“请求批准”模式发送：

```text
请加载 shell_run，通过终端执行下面这一条命令，确认创建 approval-ask.txt，再报告结果。不要改用 file_write。
printf 'approval-ok\n' > approval-ask.txt
```

预期：出现该命令的批准请求；先检查完整命令，再点“仅本次允许”。终端 B 验证：

```sh
cat "$HARNESS_DEMO_ROOT/controls/approval-ask.txt"
```

切换为“帮我批准”，发送：

```text
请通过 shell_run 执行 printf 'assisted-ok\n' > approval-assisted.txt，并报告结果。不要改用其他文件工具。
```

查看审核记录：独立审核可能允许、拒绝或交还用户决定。预期是有实际审核依据；不是要求每次自动通过。审核失败需要人工处理也符合当前设计。

获准并执行成功后，在终端 B 检查：

```sh
cat "$HARNESS_DEMO_ROOT/controls/approval-assisted.txt"
```

切换为“完全访问权限”，在弹窗点击“允许当前对话完全访问”，发送：

```text
请通过 shell_run 执行 printf 'full-ok\n' > approval-full.txt，并报告结果。
```

预期：这条普通命令不再逐次等待批准。终端 B 检查后，把权限切回“请求批准”：

```sh
cat "$HARNESS_DEMO_ROOT/controls/approval-full.txt"
```

讲解：“三种模式改变的是哪些操作需要审批。普通工作区内的文件读写在请求批准模式下也可能直接允许，因此这里专门用终端命令观察区别。完全访问不代表取消相册等硬限制，也不替代网站发布确认。”

### 20. Skill 可加载，越权读取仍拒绝

在同一控制工作区，发送以下内容，替换风险 Skill 的实际调用名：

```text
这是权限拒绝测试。请先加载“[photo-risk 的实际调用名]”，报告其中有哪些要求。然后让一个通用后台助手也加载这份 Skill，再尝试通过 file_read 读取 Photos/synthetic-face.txt。只尝试这一个测试路径，收到拒绝就返回原始错误，不换路径、不调用终端绕过，也不要生成真人头像。
```

预期：Skill 内容可以读取；后台助手请求测试相册路径时被拒绝，文件内容不返回。材料只是占位文本，不需要放入任何真实照片。查看工具记录确认是路径策略拒绝，而不是仅因“没有这个文件”。

再在“完全访问权限”模式对同一路径做一次 `file_read` 尝试，仍应拒绝，结束后恢复“请求批准”。相册硬限制与普通操作审批是两层规则。

不同角色的权限范围可在任务树的“材料与工作范围”中检查。子助手不会因为 Skill 写着“我是头像助手”就自动获得额外目录或照片权限。

### 21. 同一次对话只回滚一个文件

确保控制工作区没有正在运行的任务。新建真实模型任务，仍选择这个工作区，发送：

```text
读取 wang.txt 和 li.txt。在同一轮执行中，将 wang.txt 的“王磊旧版”改为“王磊新版”，将 li.txt 的“李明旧版”改为“李明新版”。只修改这两个文件，保留换行。完成后逐个读取确认，并结束本轮。
```

等所有任务和资源结束，终端 B 执行：

```sh

cat "$HARNESS_DEMO_ROOT/controls/li.txt"
```

预期：分别是“王磊新版”“李明新版”。

点击“修改记录 → 查看修改”，展示两个文件的前后内容。点击“选择文件撤销”，只勾选 `wang.txt`，点击“撤销所选 1 个文件”。再次执行上面两条 `cat`。

讲解：“回滚记录来自本地 Git 快照，展示前后内容并按文件恢复。已经被后续编辑过的文件会先检查冲突，不直接覆盖。它不能回滚已经发到外部服务的操作。”

### 22. 打断、改方向和资源回收

这项使用预设流程。点“新建任务”，选择“Demo · 标准”、示例工作区，点击“试试一个演示任务 → 打断与资源回收”。

3. 将主输入框“选择模型”切换为“Demo · 紧凑”。观察交接记录和实际模型变化。
4. 到“产物”查看 `model-handoff.json`，检查交接内容与目标窗口。

预期：压缩后仍保留当前目标、约束和必要执行状态，原始材料可以回查；切换先检查目标容量，无法容纳必要信息时拒绝，仍保留原模型。

使用真实模型时，可在有足够历史的任务追加：


这条需要在网站任务中发送，或者使用包含该要求的任务。预期：查到本任务原始历史，给出证据。主模型切换不自动更换所有后台助手；指定助手切换已经在第 8 步单独测试。

讲解：“我们尽量保住任务状态和可追溯材料，不能保证换成能力更弱的模型后答案质量完全一样。”

场景测试名称里的 A、B、C、D、E、F 对应截图中的单人失败与回滚、定向补充、权限、恢复、换模型、后台继续。演示时展开相关测试名称，比只放一个绿色总数更容易说明测了什么。

## 六、录屏怎么组织，结果怎么记录

建议先完整手测，再录制。录制前保存密钥配置，清楚区分真实 API、主动注入的故障和预设模型；等待真实出图的部分可以剪辑，但保留调用、模型、任务编号和结果。

20 分钟可以这样安排，时间只是剪辑建议：

| 时段 | 展示内容 | 要留下的证据 |
| --- | --- | --- |
| 0—2 分钟 | 工作台、任务目标、模型与工作区 | 实际模型、八人名单、本地工作区 |
| 2—7 分钟 | 后台分工、单人错误、定向补充、换模型 | 任务编号不变的其他助手、错误记录、补充生效和实际新模型 |
| 7—11 分钟 | 头像版本、后台搭站、局部恢复、预览和批准 | 八人预览、王磊单人变化、关页后保留的批准请求 |
| 11—15 分钟 | Skill 分层目录、导入冲突、独立评估和阶段加载 | 原文、人的处理决定、报告依据、实际加载文件 |
| 15—18 分钟 | 权限拒绝、单文件回滚、打断和压缩 | 拒绝原因、前后文件、资源归零、交接记录 |
| 18—20 分钟 | 宠物、规模和测试结果 | 历史证据、反馈、实际加载数量、测试结果 |

发布没有完成时就停在本地预览或待批准，不配上“已经上线”的解说。两种模型没有都调用成功，就不说切换已经验证通过。

每一项手测只需记四件事：用的任务、实际操作、实际结果、录屏片段或失败记录。状态写“通过 / 未通过 / 未测试”，真实服务没配好应记未测试，不能归入通过。

遇到问题按现象处理：

- **网页打不开或端口占用：** 先查第 1 步健康接口；已有应用就复用，不同时开 `npm start` 和 `npm run dev`。
- **模型只介绍能力、不操作：** 检查是否误选 Demo；真实模型再查测试调用及工具错误。
- **后台补充来不及：** 子任务已结束就重做；要证明运行中生效，重录第 8 步或运行对应时序测试。
- **工作区被占用、回滚按钮不可点：** 先结束或停止使用该工作区的任务，等资源清理完成。“新建任务”不会停止旧任务。
- **选择图片后预览没变：** 旧预览固定保存，需要重新生成，而不是刷新浏览器。
- **批准过期或发布不确定：** 修改内容后重新检查并申请；外部结果不确定时先查供应商状态。

结束录屏后，先在界面停止尚未结束的测试任务，等资源归零，再关闭桌面宠物和终端 C 的故障服务。最后按需关闭终端 A。保留临时目录中的材料、证据和网页中的任务记录，方便复核。
