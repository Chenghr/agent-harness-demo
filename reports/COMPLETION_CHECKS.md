# 成果检查补充记录

本次在第一轮 TaskController 与 Agent Loop 拆分基础上，补上“执行收尾后检查成果”的设计和实现。供团队阅读的简明说明见 [核心功能说明](1-核心功能说明.md)。

## 执行规则

Agent Loop 继续返回“继续”或“候选最终回答”。TaskController 先检查待收消息、模型切换、子任务和登记中的在途工作，然后通过 `verifyCompletion` 检查成果。检查期间使用 `verifying` 状态，结束时重新核对执行是否有效、输入和成果是否变化。

检查返回逐项名称、通过/失败/未知、依据及总体结论。结果必须非空且格式完整；包含失败项不能自动通过，未知项或检查器异常进入 `needs_review`。这个状态表示执行停止、结果保留，尚未被自动检查或用户接受；它不会占用一个持续运行的模型循环。

明确失败时，控制器将具体问题作为运行时资料加入下一步模型输入，默认最多允许两次自动返工。上限由 TaskController 构造参数控制。达到上限后，保留失败依据并等待用户提出修改要求；不会无限让模型自我确认完成。

验收结论绑定当前执行、要求版本及相关文件内容。检查期间变化会放弃旧结论；最终复核与完成提交之间没有异步等待。待验收结果也要核对版本，过期、重复或停止后提交的验收不能使任务完成。

## 检查标准从哪里来

`server/completion-checks.mjs` 位于核心之外，提供现有示例的检查。只有原始要求匹配的预设场景启用其自动标准：

- 完整任务链：重新运行四项原始购物车测试，检查原有测试未修改、所有测试实际执行并通过，保存测试输出。正常退出但没有执行完整测试也不能通过。
- 安全反例：检查对应拒绝记录及原始文件未改动。
- 千次调用：检查成功示例计算次数和工具失败计数。

自由任务、未配置规则的分析任务、改变过要求的任务采用用户验收，避免用旧标准证明新要求已经完成。后台任务没有专属标准时，将待核实结果交给父任务；父任务按自己的标准处理成果。

可信业务代码可通过 Harness 的 `completionCheck` 参数接入自己的检查函数。函数接收当前任务、Agent、候选说明和取消信号，返回检查报告，负责等待自身工作结束。该入口没有暴露为模型工具，没有安装任意验证脚本或自动 LLM 裁判。本次没有自行规定隐私实体类别、标注规范或数据格式。

## 用户验收

新增 `POST /api/sessions/:id/review`，参数为当前 `reviewId`、`decision`（`accept` 或 `revise`），修改时必须填写 `feedback`。明确失败项不可一键接受；`revise` 通过现有用户消息入口继续任务。

前端用独立的 `completion-review.tsx` 展示检查范围、依据、待验收状态和修改输入。自动检查通过与用户验收分别记录 `acceptedBy: checks/user`。用户接受未知项后仍保留原自动检查记录，不把未知项改写为自动通过。验收不会增加工具授权。

快照保存检查记录和验收方式；旧任务不会自动补验收，没有检查记录的历史完成任务会在界面明确提示。

## 验证

先新增控制器失败用例，确认原实现不会调用成果检查，随后实现对应规则。具体检查接入后，又复现并修复了“退出码为零但原有测试未执行”的误判。

本次新增 20 项测试：10 项控制器测试、9 项实际 Harness 测试、1 项 HTTP 验收与保存测试。第一轮消息时序测试注入明确的测试检查器，继续独立验证原有控制行为；实际成果检查由新增测试和完整示例任务验证。

- 完整回归：71 项全部通过，约 15 秒，包含 1,005 次示例工具调用。
- 运行时及前端 TypeScript 检查：通过。
- lint：通过，无警告。
- 静态前端构建：通过。构建的预渲染步骤需要本机临时监听；首次受限运行报 EPERM，允许本机监听后成功。
- 浏览器：在独立临时服务中，使用明确标注的模拟回答，验证自由任务待验收、提交修改、再次返回结果、人工验收后完成；并验证失败检查没有直接通过按钮。已查看页面截图并修正通过后的提示文字和颜色，再重新加载检查。

本次没有调用真实模型服务，没有更新原交付 ZIP，也没有用这些测试证明真实模型的业务质量。

## 能保证到哪里

自动完成表示任务配置的检查项目通过，不代表任意自然语言要求都已全面验证。程序可以确保“没有通过记录就不自动完成”，但检查标准的覆盖面需要业务方明确。

当前指纹读取工作目录顶层文件，结合框架维护的要求、文件修改和模型等版本；尚未通用覆盖嵌套目录、外部系统和全部产物。检查函数需要遵守取消约定；任意忽略取消且永不返回的自定义函数不能由控制器强制终止。

检查使用原有受控本地执行环境，测试输出也不是恶意代码隔离的安全证明。此前确认的进程组清理、子任务初始化、能力版本和历史证据等问题仍需后续处理，未因增加成果检查自动解决。
