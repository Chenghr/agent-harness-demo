# 核心机制与原设计的对照核查

核查日期：2026-09-10。

状态说明：本文保留第一轮重构前的核查基线，代码行号也对应当时版本。随后已修复本报告中的最终消息遗漏与子任务失败投递问题，并抽出 TS 控制器和循环；最新实施与测试结果见 [第一轮重构记录](FIRST_ROUND_REFACTOR.md)。其余差距未因本次拆分自动解决。

本轮以 [最初设计文档](../HARNESS_DESIGN.md) 为基准，读取当前后端、接口和测试，并复核可控失败场景。只增加核查材料，没有修改运行代码、前端或原设计。

原文区分基础实现、可选增强和扩展思路，不能将三者合并为未完成清单。模型切换虽然在原文 §8.7、§10.1 中属于可选项，但用户后来明确选择实现兼容模型间的手动交接，本轮将其纳入需要完成的范围。用户最新确认的 Work Agent、双界面与隐私实体数据集场景，改变展示与业务适配，不替代原有核心机制要求。实体体系、数据生成方式及最终格式仍未确定，本报告不补充这些业务设计。

## 核查结论

当前已形成自行实现的 Agent loop、后台任务、能力目录、上下文和模型适配器骨架，有真实文件与进程操作，也有自动化测试。对照原设计，尚不能认定核心机制已完整落实：存在已复现的运行正确性缺陷，以及原文要求做实但目前只简化覆盖的加载、版本、结果和资源管理机制。

| 机制及原设计位置 | 当前实现 | 结论 |
| --- | --- | --- |
| Agent loop 与用户打断，§2.3、§4 | 同一 loop、异步请求、epoch、取消信号、追加与停止入口 | 主路径已实现；最终消息消费和通用改方向语义不完整 |
| 后台 Agent 与资源管理，§5 | 任务树、独立历史、管理工具、受控进程、并发限制 | 主路径已实现；初始化失败、失败投递、终态收敛和进程组清理有缺口 |
| 千级工具，§6 | 千级目录、关键词搜索、按需 schema、校验与分发 | 容量路径已验证；工具版本固定、模型侧完整发现入口与适配器边界未做实 |
| 千级 Skill，§7 | 实际生成包、按需正文、Agent 作用范围、正文快照 | 容量路径已验证；通用包解析、资源版本及脚本入口未完成 |

## 逐项对照

### Agent loop 与用户打断

原文要求区分补充、立即改方向和停止；同一 Agent 只保留一条有效 loop；旧轮次不能派发新操作；结束前处理未消费输入、必要后台结果和在途资源。

[运行循环](../server/harness.mjs#L269) 已有控制器去重、epoch、AbortController 和每项调用前检查；[模型适配器](../server/models.mjs#L286) 会拼接并检查完整工具参数。取消后补齐未执行调用的取消结果，保留调用与结果关系。相关测试覆盖迟到响应、连续改方向、断流和迟到授权。

目前存在以下差距：

- 最终回答分支检查了模型切换与活跃子任务，却没有检查 `pendingMessages`。复现中，用户追加的一条消息尚未消费，任务已经 completed。这是原文 §2.3、§5.2 所要求的完成边界缺陷。
- 只读、允许修改、取消后台等自然语言快捷行为依赖有限中文正则。任意业务规则变化仍依赖下一次模型理解，尚无通用的冲突后台工作重定向机制。
- 用户要求以累积文本保存，没有独立表达哪些旧要求已被新要求替代。对于数据集规则变化，应保留原始消息与生效版本，再由业务层说明变更影响，不能用关键词替代业务判断。
- 当前 `session` 对象同时承担对话与任务范围，完成后继续消息会复用既有对象和预算。原文会话、任务、轮次的概念尚未完整分开；继续原任务与建立新任务时的授权、预算延续语义需先明确，不必为此增加多个服务。

建议先统一完成状态的提交入口：有待消费消息或必须处理的后台结果时继续决策，资源未确认收敛时保留相应状态。收到消息、消息已消费和变更已处理应能够从事件中分别核查。任意外部写入回滚、脚本断点恢复仍保留为扩展。

### 后台 Agent 与资源管理

原文要求归属登记、启动失败闭环、独立上下文与权限、成功和失败结果投递、关闭后禁止派生、取消传播与实际回收。后台结果还需记录所依据的输入版本。

[创建与管理入口](../server/harness.mjs#L883) 已提供创建、状态、消息、取消和等待。主子 Agent 复用 loop，模型槽位在请求完成后释放，等待后台结果不占模型槽位。子 Agent 使用独立副本，直接文件写入被拒绝；模型、工具执行、Agent 数量和深度均有上限。

当前有三类运行缺陷：

- 初始化先登记节点，再复制固定示例文件。文件复制失败会留下 idle 节点及未闭合的父任务等待；上一轮复现本次仍成立。
- [成功分支会投递父任务消息，失败分支没有相同投递](../server/harness.mjs#L435)。本轮新增复现：子任务在父模型生成最终回答时失败，父邮箱为空，父模型只调用一次，整个任务直接 completed。错误已在事件中保存，但尚未保证主 Agent 处理错误。若父任务此前进入等待或继续下一轮，仍可能读取失败状态，不能据此概括为所有失败都不可见。
- [ProcessManager](../server/core.mjs#L206) 将组长进程的 `close` 当作清理结束。普通同组后代若不持有输出管道，可以在资源登记被删除后仍然存活。这发生在当前声明支持的受控 POSIX 进程组内，不属于主动逃逸的扩展边界。

版本与限制也有简化：`baseRevision` 仅与整个 `workspaceRevision` 比较，后者只在受控文件写入时增加；没有实际依赖文件的哈希或快照引用，也没有将用户要求版本纳入后台结果的过期判断。模型和进程有单次超时，任务有调用/轮次上限，但缺少整个任务或后台等待的时间边界。Agent 上限按累计登记节点计算，尚未区分存活数量与历史数量。

建议由同一 Supervisor 路径处理成功、失败、取消和启动失败，确保结果登记、通知父任务与资源释放都有对应处理。根据原文 §5.3 补足输入依据；迁移到隐私实体场景时，材料版本和标注要求版本可作为结果检查依据。自动判断任意业务依赖、并行合并共享文件、跨机器恢复不纳入本次基础范围。

### 千级工具的发现、加载与分发

原文要求大目录、小活跃集合、逐步搜索和分类回退、来源消歧、固定定义版本、统一参数/权限检查、可解释结果与有界执行。

[目录实现](../server/catalog.mjs#L240) 有 20 个核心工具和 1,200 个生成计算工具。生成工具有不同名称和定义，复用五种计算实现，明确标为 fixture。当前限制附加活跃工具数量，不会将整个目录的 schema 注入模型。[调用入口](../server/harness.mjs#L471) 检查加载状态、参数、轮次和相关授权，并保存结果。

尚未做实的内容：

- 活跃工具只保存名字。后续输入组装和调用仍读取当前目录定义，没有绑定加载时的 schema 和执行器版本。本轮将临时目录中的工具定义由版本 1 替换为版本 2 后，未重新加载的调用立即受到新定义校验。这是对已有版本差距的实测，并非当前系统已经支持热更新。
- 底层目录与网页查询支持分类和分页，但[提供给模型的搜索工具](../server/catalog.mjs#L33) 只有 query/kind，执行时固定返回前八项。模型可改写查询，但无法显式翻页或按分类浏览，原文的渐进探索入口尚不完整。
- 执行路由仍集中在 `Harness.execute` 的静态分支。新增工具需同时修改核心目录和循环所在文件；权限检查与并发限制依赖具体工具名，没有形成清晰的适配器注册契约。
- 校验器覆盖当前使用的 JSON Schema 子集，不能据此承诺通用 Schema 支持。同来源/跨来源同名冲突处理、可发现权限过滤也没有完整机制；当前本地单用户目录不等于多用户能力目录。
- 已有调用与轮次上限，但同类重复失败主要依靠模型调整和总预算停止；没有通用重试或外部未知结果处理协议。

建议先分离定义、已加载版本和执行器注册，合并网页与模型的能力加载入口，补齐模型可用的发现参数。Schema 可采用经过验证的实现，或明确支持范围并拒绝不支持的定义。MCP 客户端与大量外部服务认证是原文的条件性适配/扩展，不应因为尚未接入而把本地路由整体认定为未实现。

容量证据需要按口径解释：既有报告验证了 1,200 个不同工具逐项加载、调用、卸载，以及 1,005 次计算调用的长程循环。本轮再次通过该长程循环测试。它们尚未覆盖同义表达、相似项干扰下的系统性检索质量，也没有把错误、取消、大输出和并发交错混合进同一长程压力验证。

### 千级 Skill 的加载与作用范围

原文 §7.2、§7.5 将 `SKILL.md` 元信息解析、逐层加载、来源版本、去重、Agent 范围、资源路径检查及受控脚本入口列为基础实现。

当前有 4 个内置 Skill 和 1,200 个生成包，均实际写入 `SKILL.md`。加载按精确名称进行，正文进入各 Agent 独立快照，卸载停止后续注入，压缩后仍从正文快照恢复。[资源读取](../server/harness.mjs#L711) 检查已加载状态、声明路径和工作包范围。

这些能力还不能等同于完整 Skill Loader：

- 元信息来自代码对象；写出的 frontmatter 没有被通用解析。启动时重新生成包，没有扫描指定目录、校验外部包或明确处理解析错误的入口。
- 正文有快照，资源清单与资源内容仍从当前包读取。本轮加载 Skill 后改动参考文件，未重新加载便读到了新内容；固定版本只覆盖正文的一部分。
- 没有 Skill 脚本的通用受管理执行入口，也没有缺失依赖报告。现有 `run_tests` 只执行固定购物车测试，不能算通用 Skill 脚本支持。
- 资源读取只返回前 2,000 字符，没有截断标记或分页；反复读取不能取回其余部分。
- 不可信标记来自预置教学样例。它说明“加载不授予权限”的演示路径，不构成自动 Skill 安全审查。

建议补齐实际包读取和解析、明确来源与重复名称处理、正文及资源版本绑定、完整资源读取，以及有范围和取消能力的脚本入口。初版只需报告缺失依赖，不需要自动安装、完整依赖求解或自动识别任意指令冲突。

### 上下文管理与压缩

原文要求预算覆盖完整请求，大输出保存后再裁剪，近期完整交互与有损摘要组合，真实状态和活跃能力重新注入，并在压缩提交前检查版本。

[ContextManager](../server/context.mjs#L65) 已将系统内容、历史和工具定义一起估算，预留输出预算；最近三个交互单元及未完成交互保留。压缩检查任务 revision、Agent epoch 和 contextVersion，变更时放弃旧摘要；授权及任务状态从程序重建。测试已覆盖压缩时改要求、未完成工具单元保留和模型切换引起的压缩失效。

当前的实质差距：

- 统一结果裁剪阈值与文件转存阈值不一致。实测 5,012 字符文件被截断后没有原文产物引用，模型无法完整读取。已转存产物具有分页入口，但并非所有截断路径都转存。
- 进程输出也设有内存截断上限，事件逐块记录同样会裁剪；不能把任何规模的进程日志都表述为完整保留。
- 摘要是按消息类型摘录，再保留末尾 5,500 字符；没有对全部被替换历史建立持久的覆盖索引，也没有逐项检查关键证据引用。原始事件存在不等于模型知道该查哪段。
- 用户补充、后台通知和运行时资料均可能以 user 消息承载，压缩再按 role 添加文字标签。虽然正文有部分来源提示，但还缺少独立的来源类型，无法仅凭 role 确定“用户已确认”。
- token 为字符启发式估算；原生模型输出块在适配后可能改变实际请求大小，因此不能宣称供应商协议层面的精确预算。活跃能力主要手动卸载，尚无原文所述的先收缩非必要注入再压缩流程。

建议首先统一大结果存储和分段读取；其次保留压缩覆盖范围、来源和证据引用，区分用户要求、后台观察与助手结论。摘要仍可采用简单方法，但应明确有损边界。无损长期记忆不属于本次目标。

### 模型切换与交接

[切换实现](../server/harness.mjs#L1098) 已支持主 Agent 手动切换，等待完整工具交互结束，准备独立候选上下文，检查目标窗口后提交。后台 Agent 保持启动模型；失败保留原模型和历史。已有测试验证了交接时授权/Skill 保留、窗口失败和不重放当前调用。

当前交接只携带旧摘要、最近三个历史单元和部分运行时事实；此前尚未压缩的较早证据会被遗漏。本轮再次复现：旧证据仍在磁盘事件中，却不在新模型输入里。切换成功提示目前比实际覆盖保证更强。

两组真实模型配置共用地址、凭据、协议和窗口参数，工具能力也由静态配置声明。适配器具有两种协议路径，但尚未完成真实模型联调、逐模型能力校验或原文提出的交接损失比较。

建议复用上下文的来源和覆盖管理，先覆盖所有待替换历史，再构建候选交接；只有结构、预算和必要能力满足要求才提交。保留当前安全边界与后台模型固定策略。实际质量需在配置模型后检查任务约束和产物，不能由“有交接 JSON”推导为回答质量不下降。自动路由、质量回切和任意跨供应商迁移仍是扩展。

### 授权、隔离与运行记录

[授权入口](../server/harness.mjs#L545) 已支持拒绝、单次、任务内指定文件和撤销，授权绑定调用参数/版本，排队写入前再次检查撤销状态。路径越界、工作区外符号链接、子 Agent 文件写入等有明确拒绝路径。

路径策略仍混用原始字符串和解析后路径：获得明确匹配授权的 `./agents/...` 写入可以绕过子目录禁止规则。这没有绕过用户授权或工作区边界，却违反当前宣称不可由授权解除的硬性策略。本次再次复现。建议统一资源标识，使硬性策略、授权匹配、审计与执行使用同一解释。

当前隔离是工作副本和进程管理，未限制任意代码的文件、网络和宿主资源访问。原文允许基础版使用可信脚本；强沙箱不是本轮应补齐的既定基础要求，但若最终决定执行不可信脚本，需要另行选择受限环境。

[事件与存储](../server/core.mjs#L112) 已有递增序号、JSONL、原始产物和临时文件替换快照；重启标记中断，不重放旧写入。SSE 重连先提供当前状态并补近期事件，不等于完整重放。现有 HTTP 测试覆盖基础重连路径。

旧活跃 action 会阻止完成记录裁剪：本轮再次复现保留 221 条记录而超过当前 200 条目标。日志读写仍同步，历史查询每次全量读取与解析文件，尚无增量读取和完整背压策略。建议分开管理在途操作与已完成记录，并按需读取历史。完整崩溃恢复、跨机器一致性和外部副作用补偿仍保留为扩展。

## 代码组织与后续处理建议

原设计 §2.2 的职责多数集中在 `Harness` 一个类内。运行时代码直接导入购物车 fixture、复制固定文件，系统提示也固定为代码助手。网页与模型分别实现能力加载，元信息记录存在差异。迁移 Work Agent 场景需要消除这些耦合，避免将隐私实体业务再加入同一个核心文件。

建议按原设计已有职责整理：会话控制负责输入与有效轮次，Runtime 负责决策循环，Supervisor 负责子任务与资源，Broker 负责执行约束与适配器，Registry/Loader 负责能力及版本，Context Manager 负责预算和证据。无需把每项职责部署成独立服务，也不以文件数量判断架构质量。优先统一状态转换、加载和结果入口，补充关键状态、工具结果及事件的接口约束；后端当前 `.mjs` 没有统一静态类型契约，lint 通过不能替代契约与边界测试。

下面是处理顺序建议，不是已经完成的变更：

1. **修正运行正确性。** 先处理消息/后台结果消费、子任务初始化和失败投递、进程组回收、路径策略与记录裁剪，将已有缺陷复现转为期望正确行为的回归测试。
