## 实现怎么组织

任务控制仍由现有控制器和循环负责。本轮只补充等待唤醒、定向消息和模型交接的缺口。默认“下一步补充”保留正在运行的其他工作；用户明确选择改变整个方向时，原来的停止与清理流程仍有效。已结束的子任务重做会产生新节点，原结果继续保留。

文件回滚先检查所选文件是否被后续改过，再恢复对应旧内容。未选文件不改；同一轮尚未回滚的文件之后仍可单独回滚。回滚后旧验收结果失效，主助手继续工作前需要重新读取文件。

全量回归还发现，新增工具说明后，固定保留最近三轮历史可能让千次调用超出模型窗口。已改为根据输入预算选择保留范围，压缩完整的旧交互并归档原文；未结束的工具交互不会被拆开或归档。额外测试验证了长工具结果、未完成交互及 1005 次调用的情况。

图片和网站能力放在独立的 `server/delivery/` 中，服务配置、供应商请求、图片版本、预览、发布、工具定义和网页接口分开维护。`greeting_site` 是祝福网站示例工具，通用任务循环没有内置“教师节”分工逻辑；其他静态网站可以使用 `site_preview`。

每次出图保存独立版本和实际模型。失败或取消不会删除成功版本，过期响应不能覆盖新的选择。主助手可以通过 `agent_spawn.images` 把指定图片版本交给后台搭站助手；后者不能读取未分配的其他图片，也不会自动取得该图片未来的新版本。这样可以完成跨助手协作，同时保留明确的材料范围。

网站预览保存固定文件副本。发布申请绑定预览、文件内容、图片选择、验收要求、发布目标和授权版本。用户批准后重新检查，只发送与预览一致的 ZIP；重复点击不会重复提交。模型没有“批准发布”工具。外部请求中断后，结果标为待核对，不自动重发可能已生效的部署请求。

## 网页怎么使用

1. 在“模型与运行设置”配置真实对话模型，再展开“出图与网站发布服务”填写图片 API 地址、模型 ID、协议和密钥。发布填写 Netlify 的已有站点 ID 与 Token。
2. 创建任务，在“图片与网站”填写八位成员和需要的字数上限，然后让助手安排工作。图片模型与对话模型可以来自不同服务。
3. 需要改某人内容时，在输入框上方选择接收助手。任务树中可以选择该助手的模型；已结束的子任务可以点击“重做此任务”。
4. 在“图片与网站”查看各版本、恢复单人的旧图并检查网站。只有点击“确认公开发布此版本”，应用才会请求发布。

实际网页验收还修复了长弹窗超出屏幕的问题，现在弹窗限制高度并内部滚动。确认按钮、图片回退和文件勾选回滚均已实际点击验证。网页测试使用明确标注的图片占位响应及测试发布服务。

## 明确的边界

图片适配器支持返回 Base64 的 Images API，当前请求一张 1024×1024 图片，接受 PNG、JPEG 或 WebP；不支持照片参考、图片编辑或供应商只返回下载地址的模式。发布适配器支持 Netlify 静态站点，需要用户已有站点，不包含购买域名或发送给老师。接口依据 [OpenAI Images 官方文档](https://developers.openai.com/api/reference/resources/images/methods/generate)和 [Netlify API 官方文档](https://docs.netlify.com/api-and-cli-guides/api-guides/get-started-with-api/)实现。

相册保护落实在文件路径、macOS 命令沙箱和出图参数上；静态扫描提供风险提示，不是完整语义审查。没有实现对任意改名文件的人脸识别，也不能保证生成模型在所有文字表达下都遵守虚构形象要求。形象是否满意、风格是否一致，仍要看真实图片并由用户确认。

关闭网页不会停止后端；关闭后端、电脑休眠或断网是不同情况。重启不会自动重放未完成的出图与发布；不确定的发布需要到供应商核对。macOS 的命令隔离已实际测试，不能把结果直接当作其他系统的隔离证明。

普通聊天中的局部修改由真实模型理解和分发，不能仅凭机制测试保证它每次都正确识别成员。已提供明确选择接收助手的入口，以及成员名单、字数和预览版本的检查。真实 API 的账号权限、响应差异、图片质量和线上发布仍需配置后联调；本轮没有使用或提交真实供应商密钥。
