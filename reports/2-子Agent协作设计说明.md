**2-子 Agent 协作设计说明**

本文说明本轮已经落实的子助手协作设计，接在《1-核心功能说明》之后。第一份文档正文保留；这一轮继续使用其中的任务控制器、Agent Loop 和成果检查，在外围补上分工、材料分配、权限限制和资源收尾。

文中的“主助手”是处理用户整体任务的 Agent，“子助手”是它为一项具体工作创建的 Agent。二者都使用模型完成工作，但创建检查、权限判断和取消处理由程序执行。

**主助手什么时候分工**

主助手根据任务决定是否创建子助手。适合分出去的是目标明确、材料可以单独提供、需要多步处理的工作。一个简单查询可以直接调用工具；需要前一步结果才能继续的工作，应按顺序进行。程序不强制拆分，也不保证多助手一定更快。

以构建隐私实体数据集为例，主助手可以把“根据给定规则检查一批样本的问题”交给子助手，自己继续处理其他独立工作；收到结果后再核对和整理。这只是分工方式的例子，本轮没有新增完整的数据集构建或标注质量评估系统。

模型创建子助手时说明这次的目标、必要背景、输入文件或产物、希望得到的结果，以及前台等待还是后台执行。分工理由可以简短填写。父任务编号、工作目录、有效权限和执行版本由程序填写，模型不能在创建参数中自行授予权限。

**默认使用通用助手，需要时再选专门助手**

默认的 `general` 是通用助手，可以直接接受临时任务。增加一种工作不需要先增加一种助手类型。当前还提供 `analysis` 分析助手和 `review` 检查助手，它们使用只读材料的限制。

助手类型只是提前保存的一份工作说明和能力配置。团队可以在应用的 `config/agents/` 中增加或修改 Markdown 文件，设置工作说明、允许的工具和 Skill、模型范围、写入范围，以及是否允许继续创建子助手。配置在后端启动时读取，运行中的助手保留当时的配置版本；修改后需重启服务才能用于新任务。

配置文件采用 `---` 包围的 JSON 文件头，后面是普通 Markdown 工作说明。当前读取器支持这一明确格式，不是通用 YAML 解析器。程序会检查名称、字段、引用的能力和预算；配置错误直接报告，不能悄悄放宽限制。`@catalog` 表示使用已登记目录的名称集合，仍需经过对应的权限和加载检查。

工作说明告诉模型“怎样做”，权限检查决定“能不能做”。即使工作说明或 Skill 要求越权，也不能改变后端的允许范围。

**子助手用哪个模型，能看到什么材料**

模型选择按三个步骤处理：本次明确指定了模型，就用该模型；没有指定时，使用助手类型的默认模型；类型配置为继承时，使用创建那一刻主助手的模型。

例如，主助手正在用模型 A，分析助手默认配置为模型 B：普通创建使用 B；这次明确指定 A，则使用 A。前提是所选模型在允许范围内、服务已配置并支持工具调用。检查不通过就说明原因，不替换成其他模型。创建后固定并展示实际模型，主助手后续切换模型不会改变已经运行的子助手。

每个子助手有自己的目标、历史、能力加载记录和工作目录。程序只复制本次明确分配的文件和产物，不再固定复制购物车示例的三个文件，也不复制主助手的整段对话。必要背景由主助手另外说明。

读取限制落实在入口上：文件读取和目录列表只展示允许的材料；历史搜索只查自己的记录；产物读取只接受自己拥有或被明确分配的产物；子助手只能管理自己的后代。上下文组装和压缩也使用同一范围，不能从全会话记录中补回未分配的资料。

文件同时检查请求路径和符号链接指向的真实位置，避免换个路径名称绕过限制。创建时保存材料内容和指纹；原材料或用户要求后来变化时，界面与返回结果提示依据已经变化，提醒主助手重新核实。文件是逐份复制的，不承诺多个源文件在外部并发修改时具有同一时刻的快照。

当前可以给运行中的子助手补充文字或调整方向；新增文件材料需要重新创建子任务。没有实现运行途中追加材料文件的接口。主助手仍可能把自己读过的信息写进背景，因此这里是接口访问限制，不是自动识别所有敏感信息的系统。

**写入、授权和再次分工怎么限制**

当前支持两种工作范围。分析助手和检查助手只能通过文件工具读取分配材料；通用助手还可以申请在自己的 `outputs/` 目录生成文件。子助手不能改写输入材料、兄弟助手目录或主任务的最终文件。主助手通过交回的产物整理最终成果。

工具是否允许使用、是否已经加载、操作是否获准，是三件分别检查的事。允许但未加载的工具要先加载；加载工具或 Skill 不增加授权。被禁止的工具既不会出现在模型可用列表中，直接构造调用也会被拒绝。预加载 Skill 来自助手配置，后续自行加载同样受允许范围限制。

写入审批仍集中在主界面。审批写清是哪个助手、准备修改哪个文件。单次批准只对应这次操作；选择继续允许时，也只允许这个助手后续修改同一个文件，不扩展到主助手或兄弟助手。用户撤权、任务取消或要求变化后，旧批准不能继续使用；排队拿到写锁后还要再检查一次。

配置支持两种审批方式：`default` 遇到可以申请的操作时等待用户批准；`dontAsk` 在尚未获准时直接返回拒绝，不弹出申请。两者都不能绕过禁止规则。当前没有“跳过全部检查”的模式。

默认子助手不能再创建子助手。团队在配置中通过 `canDelegateTo` 明确允许后，才开放相应类型，同时继续检查深度、数量和调用预算。下一层允许的工具、Skill、模型和写入范围只能在祖先范围内收窄，不能换一个助手类型就取得更大的权限。

只读限制针对模型可调用的文件入口。现有测试工具仍会执行工作目录中的代码，脚本可能有额外副作用；独立目录和进程组不等于操作系统沙箱。本轮适用于受控本地演示。

**前台、后台怎样返回结果**

前台和后台使用同一套任务控制器和 Agent Loop，只改变主助手怎样接收结果。

前台创建后，原工具调用等待子助手结束，再把结果返回给主助手。这段等待不占模型请求名额，也不占命令执行名额。测试已验证只有一个模型请求名额时，主模型可以发起前台委派、让子模型完成、再继续处理结果。

后台创建后立即返回任务编号，主助手继续执行其他工作。子助手结束时，程序把结果加入主助手的消息队列；主助手在下一次决策前接纳。主助手已经有执行在运行时，不会再开第二个主循环。

一个子任务只登记一份结束结果，带稳定结果编号、实际模型、要求与输入版本、产物引用和资源清理情况。前台通过原工具返回，不再重复发送后台完成消息；后台通过消息队列通知，重复查询和等待不会重新投递。较长结论保存为可回读的产物，给模型的返回内容保留摘要和引用。

子助手返回结论不代表结论已经正确。没有专门检查规则时，结果标为待核实资料，交给主助手对照证据处理；最终成果继续走第一份文档里的检查和验收。一个子助手失败会作为结果交回，不默认取消无关兄弟。主任务完成前，仍需处理未结束的子任务和待接纳结果。

给子助手追加说明时，`append` 在下一次决策前接纳；`steer` 使旧轮次失效，取消它下面的旧工作，再按新说明继续。两种消息都不能扩大权限。已经结束的子助手保留结果，追加工作使用新子任务。

**创建、取消和资源回收怎样收尾**

管理程序按“检查请求 → 登记归属并占用名额 → 准备材料 → 启动执行”的顺序创建子助手。同一父执行中，同一工具调用编号的重试返回原任务，不重复创建。未知类型、禁止模型或不合法参数直接拒绝；登记后的材料准备失败，会保存失败结果并释放名额，不留下永久等待的节点。

取消某个分支时，先标记它和后代不能继续派生，再取消执行并等待清理。创建时也检查全部祖先是否仍然开放。这样，即使取消与创建发生在相邻时刻，新工作也不能逃出原任务的管理。重复取消共享同一次关闭过程。

用户给主任务追加普通说明时，不自动取消后台工作；主任务立即改方向时，本轮采用明确规则：取消旧方向下仍在运行的子任务，保留已有文件和证据，再由主助手决定新的分工。停止整个任务则关闭整棵任务树。服务正常退出也会清理受管理工作，浏览器断开不代表停止任务。

命令主进程退出后，进程管理器还会检查同一进程组中的后代。先请求退出，必要时强制终止，确认退出和输出管道收尾后才移除资源记录。测试覆盖后代继续占用输出管道，以及后代关闭输出管道但仍在运行的情况。

执行结果与资源清理分别保存。不能确认回收时保留资源记录、显示异常，并暂停该任务新的写入、命令执行和委派，阻止它被判为全部完成。已完成写入不会因为取消自动回滚。

历史结果不占用存活子助手名额，初始化、运行和清理中的子助手仍占用。当前工程默认最多 8 个存活子助手、2 个并发模型请求和 4 个并发命令；配置启用嵌套后最多两层。每个子助手还有运行时长、轮次和调用预算，后代调用同时计入祖先及全任务预算。这些数值是当前代码配置，不是课程要求。

本轮只保证当前后端进程管理的工作。后端被强杀、主机崩溃、脚本主动脱离进程组、远端操作无法取消等情况，需要更强的执行环境或外部监督；本轮没有实现。重启后保留记录并标记异常，不根据历史 PID 直接杀进程，也不自动重放未确认操作。

**代码怎样分工，怎样验证**

| 代码 | 负责的事情 |
| --- | --- |
| `server/runtime/agent-definitions.ts` | 读取助手配置，检查内容，保存配置版本 |
| `server/runtime/agent-access.ts` | 检查允许的工具、Skill、文件和产物范围 |
| `server/runtime/subagent-supervisor.ts` | 管理父子归属、创建、名额、取消和结果登记 |
| `server/runtime/process-manager.ts` | 启动受控进程，跟踪退出和资源清理 |
| `server/subagent-workspace.mjs`、`workspace-access.mjs` | 准备指定材料、检查真实路径和材料变化 |
| `server/subagent-adapter.mjs` | 把协作管理接到现有模型、上下文、存储和结果通知 |
| `server/runtime/task-controller.ts`、`agent-loop.ts` | 继续负责单个助手的执行和成果检查 |

协作核心使用 TypeScript，通过接口调用材料准备、任务控制器和资源管理。它不依赖购物车文件名、前端页面或模型 SDK。`Harness` 仍负责组装和工具分发，授权等既有逻辑还在其中；本轮没有完成全部后端的拆分和类型化。

界面沿用任务卡片，直接显示目标、状态、助手类型和实际模型；展开可以查看材料、工作范围、预期产出与清理情况。手动创建默认后台执行，可填写临时目标、选择助手类型和输入文件。模型工具及 HTTP 接口同时支持前台与后台。

本轮先用失败测试确认旧行为的缺口，再修改实现。测试覆盖临时任务、配置错误、模型选择、上下文与资料隔离、权限收窄、撤权与写锁、路径别名、前台等待、后台结果去重、准备期间取消、启动失败、名额释放及进程组清理。完整测试、类型检查和构建结果记录在项目《实现说明》的验证部分。

真实模型能否合理分工、给足材料、正确使用子结论，需要配置 API 后另外评测。当前确定性测试和模拟演示验证的是执行机制，不是模型自主协作的回答质量。
