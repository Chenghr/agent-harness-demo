# 当前实现审查

历史基线说明：本文记录第一轮重构前的审查。后续已修复最终补充消息遗漏及相关后台结果投递问题；当前变更与验证见 [第一轮重构记录](FIRST_ROUND_REFACTOR.md)。其余问题仍待处理，本文保留原复现与当时行号。

本次对照 `HARNESS_DESIGN.md`、`IMPLEMENTATION.md`、运行时代码和现有测试，核查功能范围与关键边界。结论是：当前属于核心机制的教学版闭环，加上手动模型交接；不是全部设计能力均已实现，也还存在需要修复的基础机制缺陷。上一轮“完成”应理解为第一版演示交付，不能作为完整功能验收结论。

本次没有修改 `server/` 或前端运行代码。新增独立复现脚本 `review-probes.mjs` 和结果 `review-probes.json`。这些脚本断言的是缺陷存在，不能当作修复后的通过测试。之前的交付 ZIP 仍是原版。

## 1. 已确认的问题

下列 7 项均通过临时工作区中的可控复现确认。优先级表示建议修复顺序；P1 应在将本版作为稳定课程演示前处理，P2 为紧随其后的边界修正。

### P1：进程退出不等于整个进程组清理完成

位置：`server/core.mjs:278–297`。

复现：一个受管理 Node 命令启动普通子进程，子进程使用 `stdio: ignore`，主命令正常退出。该子进程没有脱离进程组，但主命令的 `close` 已触发，ProcessManager 删除了资源登记并返回成功。

实测：主命令退出码 0，资源列表数量 0，后代进程仍存活。现有测试只覆盖后代继续持有 stdout 管道的情形。当前界面“无存活工具进程”的信息因此可能不准确；这超出了文档已披露的“主动脱离进程组或主机故障”边界。

建议：由独立执行范围管理整个进程组，组长退出后仍检查并处理剩余后代，不能仅以组长的 `close` 作为整个执行范围的完成依据。Demo 的受控 POSIX 环境可先实现组级退出清理；任意逃逸与强杀兜底仍交给外部监督器或容器。

### P1：最终回答返回时，可能遗漏已经收到的补充消息

位置：`server/harness.mjs:403–444`、`1018–1064`。

复现：模型请求进行中，用户选择“下一步补充”发送新要求，然后当前模型返回不含工具调用的最终回答。消息已经进入 `pendingMessages`，但结束分支只检查模型切换和活跃子任务，没有检查未消费消息。

实测：任务标记 completed，模型只请求了一次，队列仍有一条用户消息。后台结果在父 Agent 生成最后回答期间到达，也走相同的待消费消息路径，需要一起覆盖。

建议：终态提交前检查邮箱和已消费的消息版本。存在未消费消息时继续决策；只有任务范围内的输入与必须收取的结果都已处理，才能提交完成状态。把这个检查与终态更新放在同一处，避免各分支自行结束。

### P1：部分文件被截断后，模型没有完整读取入口

位置：`server/harness.mjs:24–26`、`511–521`、`732–750`。

`file_read` 只在内容超过 8,000 字符时生成原始产物；但工具统一返回逻辑在序列化结果超过 2,400 字符时就将整个结果变成 preview。因此中等长度文件会提前截断，没有 artifactId，也不支持按偏移读取。

实测：读取 5,012 字符文件，只返回约 2,438 字符的 JSON 结果，原始产物数量 0，末尾证据不可见。对这种文件重复调用仍只能得到同一前缀。

建议：统一结果裁剪协议，在任何截断前保存完整原文并保留稳定的 artifactId、长度、偏移或下一页信息；`file_read` 与 Skill 参考资料读取支持分页。当前 `skill_read_resource` 直接截取前 2,000 字符且未返回截断标记，也应使用同一机制。

### P1：子任务初始化失败，会留下永远等不到结果的节点

位置：`server/harness.mjs:897–914`、`954–974`。

复现：主示例工作区缺少 `README.md`，调用 `spawnAgent`。代码先把 Agent 放进任务树，再复制文件；复制失败后没有回滚节点或记录失败终态。

实测：任务树保留一个 idle 子节点，没有运行控制器；父任务 `waitChildren` 把它当成仍未结束的任务，持续等待。文件缺失、权限或磁盘错误都可能触发这一初始化失败路径。

建议：先准备工作区、再正式注册并启动；或在初始化异常时把已登记节点标记为失败并清理临时资源。所有创建结果必须有可观察的成功或失败状态。

### P2：模型交接会直接遗漏尚未压缩的较早证据

位置：`server/harness.mjs:1123–1161`。

交接使用旧摘要、最近三个历史单元和运行时事实，再用这些内容替换整个活跃历史。较早但还没被压缩进摘要的记录，会从新模型输入中直接消失。原始日志仍在，但新模型并不知道缺了哪一条，不能依赖它自动回查未知事实。

实测：历史中放入一条较早的已确认事实，再加入六条普通消息，在尚无摘要时切换模型；该事实还在原始事件里，但不在交接上下文中。这是交接覆盖不完整的问题，与模型自身能力差异不同。

建议：交接前覆盖所有待替换历史：近期保留原文，其余先进入摘要或结构化证据索引，明确记录覆盖的历史单元。准备和预算检查通过后再提交，失败时保留旧上下文。自动质量评分仍可以作为后续扩展。

### P2：权限规则使用未规范化路径，存在路径别名绕过

位置：`server/harness.mjs:545–556`、`763–772`。

路径安全检查会解析实际目标，但子任务目录禁止写入规则仍检查原始字符串的 `startsWith('agents/')`。`./agents/...` 不符合这个前缀，却解析到同一个受保护目录。

实测：给该明确路径配置任务授权后，`./agents/review-child/cart.mjs` 写入成功。它没有绕过工作区边界或授权本身，但绕过了宣称不能被授权解除的子任务目录保护。

建议：统一生成规范化的资源标识，用同一标识做硬性策略检查、授权范围匹配、审计和最终执行；仍需保留符号链接检查。不要在不同阶段分别解释路径字符串。

### P2：一条较早的活跃调用会阻止已完成记录裁剪

位置：`server/harness.mjs:488–494`。

当前仅从 `actions` 队首删除终态记录。如果最早记录仍在执行，例如主 Agent 在等待后台任务，后面即使有大量已完成调用，也无法被裁剪。

实测：保留一个进行中的等待操作并完成 220 次读取，活跃记录数组保留 221 项，突破文档中的 200 项目标。单任务总调用预算仍提供最终上限，因此不是无限增长，但现有千次测试没有验证这种交错场景。

建议：把在途操作与最近已完成记录分别存储，已完成记录使用独立环形缓冲；完整审计历史继续落盘。不要让一个长任务阻塞整个历史回收。

## 2. 预计功能完成情况

| 设计项 | 当前状态 | 主要差距 |
| --- | --- | --- |
| 自行实现 Agent loop | 教学闭环已实现 | 结束边界遗漏消息；与购物车业务仍耦合 |
| 用户打断、停止、追加 | 基础路径已实现 | 追加消息的收尾竞态需要修复；自然语言快捷控制采用有限正则 |
| 后台 subagent | 创建、消息、取消、等待、独立上下文已实现 | 初始化失败闭环、整个进程组的资源确认有缺陷 |
| 千级工具 | 目录、检索、加载、分发和容量验证已实现 | 1,200 项为生成计算能力；执行器仍为静态分支，没有外部工具模块或 MCP 接入 |
| 工具来源与版本 | 元数据已记录 | 活跃工具只保存名称，定义仍从当前目录读取，尚无真正的版本固定与兼容检查 |
| 千级 Skill | 生成文件、按需加载、去重、作用域、参考资料读取已实现 | 元数据来自代码生成对象，没有通用 SKILL.md 导入/解析；缺少受管理的 Skill 脚本执行和缺失依赖检查 |
| 上下文管理 | 有损压缩、当前状态注入、日志保留已实现 | 摘录式摘要；部分输出截断缺少原文入口；token 非精确计数 |
| 模型切换 | 手动交接与窗口检查已实现 | 未压缩历史覆盖缺口；真实服务和回答质量未联调评测 |
| Tool call 安全审查 | 参数、路径、身份与授权的确定性检查已实现 | 无通用脚本语义审查；存在路径别名问题 |
| Skill 安全审查 | 来源记录和明确标注的反例已实现 | 恶意样本标签是预置的；没有自动审查、签名或导入检查流程 |
| 用户授权 | 拒绝、单次、当前任务内指定文件、撤销已实现 | 没有完整多用户/RBAC、OAuth 或多套外部凭据管理 |
| 沙箱 | 独立目录与进程生命周期管理 | 未实现限制任意代码文件、网络和资源访问的安全沙箱 |
| 可靠性增强 | 日志、快照、SSE、重启中断标记已实现 | 无完整崩溃恢复、幂等外部写入、未知结果协议；读写日志仍同步且全量查询 |
| 趣味性 | 运行面板和活动指示已实现 | 宠物及多状态动画未实现，原设计中属于可选增强 |

未做的生产能力不是都要补进 Demo。跨机器调度、主机强杀后的恢复、任意代码安全隔离和通用无损模型迁移，原设计已作为扩展边界。相对而言，Skill 解析与脚本入口、工具版本固定等属于基础设计描述过但当前仅简化覆盖的部分，应明确列为差距。

## 3. 建议的优化顺序

**先修运行正确性。** 优先修复前四项 P1，再修模型交接、规范化权限和记录回收。每个复现转为期望正确行为的回归测试，加入“主任务与子任务交错”“消息恰好在最后响应前到达”“资源启动失败”等时序组合。现有 35 项测试仍通过，不能用这个数字替代边界验证。

**再把框架与演示业务分开。** 将购物车场景移到示例层；用工具描述加执行器注册表替代 `Harness.execute` 中不断增长的分支；合并网页加载能力与模型加载能力的重复实现。实现扫描指定目录的 Skill Loader，解析元信息、固定正文及资源版本，并返回明确的格式/依赖错误。工具的定义版本与执行器版本一起固定，而不是只有展示用版本字符串。

**然后增强展示和模型接入。** 为模型分别配置协议、窗口、地址和凭据引用；补模型输入、交接内容和压缩覆盖范围的检查视图；验证真实服务的多轮工具调用。增加少量对任务有不同用途的真实工具及 Skill，再用生成目录做容量测试，避免把容量数字讲成业务丰富度。浏览器交互测试与视觉验收也应补充。

**最后选择额外亮点。** 若需要展示更强的安全性，可以做可解释的策略审查页和 Skill 导入检查；若允许执行外部不可信代码，再接具体沙箱。趣味性可做由同一运行状态驱动的小型宠物，不应优先于消息、资源和证据链修复。外部认证体系、分布式调度和完整恢复继续保留为答辩扩展思路即可。
